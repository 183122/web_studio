# ADR-0013: Billing, metering, operator access, privacy and audit integrity

- Status: Accepted (Phase 6)
- Context: spec M03 (billing), metering, super admin + support access, PDPA controls, audit integrity, observability; J7. Billing activation, production deployment and destructive changes need explicit approval.
- Decision:
  1. **Billing behind an adapter** (`PaymentProvider`). Only a `test` provider exists: hosted checkout is a studio page that simulates the payer and emits **signed webhooks** through the same verification path as an external provider. It is refused when `APP_ENV=production`, so billing cannot be "activated" by accident. A real (Thai-compatible) provider is a new adapter + secrets + approval.
  2. **State changes only from verified webhooks**: HMAC-SHA256 `t=,v1=` with a 5-minute replay window; event ids stored with a unique key (idempotent); amount and currency must equal the invoice or the event is recorded as `rejected`. The checkout return URL only shows "waiting for confirmation".
  3. **Invoices**: prices exclude VAT; 7% VAT rounded half-up per invoice; buyer tax details snapshotted at creation; tax-invoice number `INV-YYYY-NNNNNN` assigned at payment from a locked per-year sequence (gap-free). Printable HTML (browser → PDF). Legal format must be reviewed by an accountant before activation.
  4. **Lifecycle**: checkout → active (period = 1 month, no proration); renewal invoices created idempotently per period and charged off-session; failures → `past_due` with retries after 1/3/7 days, then `expired`; cancel at period end; one 14-day trial per organization. **Downgrade = plan change only**: data is never deleted; entitlement checks block new usage above the free limits.
  5. **Metering**: `usage_counters(org, metric, YYYY-MM)` incremented with single atomic UPDATEs (no lost counts). Published-site requests and bandwidth, publish seconds, admin AI-credit grants. Soft limit at 100% (e-mail at 80%/100% once per period); hard limit at 150% for site traffic (site shows a 503 notice, data untouched); publish minutes are a hard limit. Countable limits (projects, records, storage, custom domains, members) are checked under the organization lock.
  6. **Operator access**: platform admins (granted via artisan only) manage organizations with mandatory reasons (audited). **Support access is approved by the organization** (owner/admin), read-only (maps to the `viewer` workspace role), time-boxed (30–240 min), revocable, never includes billing. Abuse reports are public (rate-limited); suspension takes sites offline and blocks publishing/checkout while owners keep read/export access.
  7. **Account security**: RFC 6238 TOTP (±1 step, replay-protected), 10 hashed one-time recovery codes, 2FA step at login bound to the session for 5 minutes; session list/revoke (raw session ids never exposed); seat-limited e-mail invitations bound to the invited address (hashed token, 7 days).
  8. **PDPA**: consent versions recorded at registration; marketing opt-in; personal-data export (JSON); erasure = immediate anonymization + owned single-member organizations soft-deleted and purged after 30 days; app owners can export/erase their end users; retention schedule for operational data.
  9. **Audit integrity**: each audit row stores a canonical snapshot and `hash = sha256(prev_hash + "\n" + snapshot)`; inserts serialize on a locked chain-head row; `studio:audit:verify` (daily + metric) detects edits, deletions, reordering and truncation. FK-nulled ids after a purge are tolerated by design.
  10. **Observability**: request ids on every response and log line (`error.requestId` for support), readiness health (DB, cache, storage; scheduler heartbeat and failed jobs informational), token-protected Prometheus metrics, JSON log channel, CI secret scanning + Semgrep SAST.
- Consequences: no proration or mid-cycle credits; no card management UI (the provider's hosted pages will own it); support access is coarse (whole organization); TOTP only (no passkeys yet).
