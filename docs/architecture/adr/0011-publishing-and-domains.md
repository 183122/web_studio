# ADR-0011: Publishing, immutable releases, runtime serving and domains

- Status: Accepted (Phase 4)
- Context: spec §8 (publishing pipeline), M26 (preview/share), M28 (custom domains), journeys J1/J6/J8/J9. Published sites must never run tenant code, must be isolated per host, must not break when a publish fails, and custom domains must not allow takeover.
- Decision:
  1. **Immutable releases.** Publishing freezes the *saved* head revision (document + content hash) into a `releases` row. A `deployments` row records each pipeline step: freeze → validate (canonical validator) → security scan (referenced assets exist/servable in the workspace, dangling internal links, public-read/permission warnings) → manifest (routes, redirects, assets, hash) → stage → smoke test (hash, every route renders, runtime bundle present) → **atomic switch** (`projects.live_release_id` under a row lock, compare-and-set against the release that was live when the deployment started) → health check through the same `SiteResolver` the runtime uses. Any failure before the switch leaves the previous release live; a failed health check switches back. Rollback = switching to an earlier `ready` release; unpublish = clearing the pointer (data kept). Runs on the `build` queue; one in-flight deployment per project.
  2. **Runtime = data, not code.** Laravel resolves the request Host → active domain → project → live release and returns an HTML shell (title/description/robots per page, strict CSP, real 404 status for unknown paths, redirects from `routes`) with the release document embedded as an inert `application/json` block (HEX-escaped). `apps/runtime-web` renders it with `@studio/renderer` in `live` mode. Workflows and internal ids are stripped from the public document. Images are served from `/_assets/{id}` only if the id is in the live release's manifest.
  3. **Data plane.** The runtime API (`/api/runtime/v1`, same origin as the site) uses the release's schema/permissions and the `production` environment; studio admins switch between preview and production data. Writes require `X-Runtime-Request: 1` (no CORS is offered, so cross-site forms cannot send it).
  4. **End-user accounts.** `app_users` per project+environment (bcrypt), opaque 48-char session tokens stored as SHA-256 in `app_user_sessions`, cookie `__site_session` HttpOnly + host-only + SameSite=Lax (Secure on HTTPS). A token is valid only for its project. Disabling or changing a role revokes sessions. Login uses a constant-time dummy hash for unknown accounts. Roles are explicit: members get only what the permission matrix grants members.
  5. **Domains.** One `domains` table for subdomains and custom domains; `active_hostname` is unique so a hostname maps to at most one project. Slugs: `[a-z0-9-]{3,40}`, reserved names blocked, released names cool down 30 days for other organisations. Custom domains need (a) a per-binding random TXT token at `_studio-verify.<host>`, (b) CNAME/ALIAS (or matching A records) to the edge, (c) a valid certificate before being served; a scheduled re-check deactivates domains whose DNS moves away. Removal releases the binding; re-adding issues a new token.
  6. **TLS.** Edge issues certificates on demand only when `GET /api/internal/tls/ask` confirms the hostname (`infra/edge/Caddyfile`). DNS lookups and TLS probing are interfaces (`system`/`static`, `probe`/`assume`) so tests and local E2E need no real DNS.
  7. **Share links (M26).** Random 40-char token, SHA-256 at rest, snapshot of the draft at creation, 1–30 day expiry, revocable, `noindex`, forms inert, signed image URLs.
- Consequences: every page view hits PHP (cheap: one indexed lookup + cached bundle); a CDN/static pre-render can be added later without changing the release model. Server-rendered HTML content (SSR) is not implemented — crawlers get title/description; body content needs JS. Real DNS/certificate issuance and production rollout are not exercised here and require explicit approval.
